## 1. Linear 为什么会让人感觉很快

在普通 Web 应用中，一次修改经常是这样的：

```text
用户点击
  → 发送请求
  → 等待服务器处理
  → 收到响应
  → 更新界面
```

网络稍慢，用户就会感到明显停顿。

Linear 采用的思路更接近 Local-first：先让本地状态和界面发生变化，再在后台完成持久化与同步。

```text
用户修改 Issue
  → 内存中的 Model 立即更新
  → MobX 驱动界面刷新
  → 生成 Transaction
  → Transaction 写入 IndexedDB
  → 加入发送队列
  → 服务器执行并分配 syncId
  → 通过 Delta Packet 广播结果
  → 客户端更新本地数据库和内存
```

用户感受到的速度来自本地即时反馈，并不意味着网络真的变快了。

## 2. 同步引擎的关键组成

### 2.1 Model 与 ModelRegistry

`Issue`、`Team`、`Comment` 等业务实体被表示为 Model。每种 Model 的属性、关联、序列化方式、索引方式和加载策略，都记录在 `ModelRegistry` 中。

可以把它理解为一套运行在浏览器里的 ORM 与元数据系统：

```text
ModelRegistry
  ├── Model 类型
  ├── Property 定义
  ├── Reference 关系
  ├── Serializer
  ├── Index 配置
  └── Load Strategy
```

系统还会根据这些元数据生成 Schema Hash，用于判断本地 IndexedDB 是否需要迁移。

### 2.2 Object Pool

加载到内存的对象按 UUID 放入统一对象池。其他 Model 引用某个 Issue 时，尽量取得同一个对象实例，而不是制造多份彼此不一致的副本。

这让响应式界面、对象关联和增量更新更容易保持一致。

### 2.3 IndexedDB 与启动恢复

客户端并非每次启动都重新下载全部数据。数据会保存在 IndexedDB 中，应用可以先从本地恢复，再连接服务器获取增量变化。

这种设计带来三个直接好处：

- 启动速度更快；
- 弱网或临时离线时仍能读取本地数据；
- 未完成的操作可以在浏览器关闭后继续恢复。

### 2.4 Lazy Hydration

数据存在本地，并不等于必须立即全部进入内存。Linear 会根据加载策略，只加载当前需要的对象；某个属性或关联真正被访问时，再从 IndexedDB 或服务器补齐。

这解决了两个不同的问题：

- **持久化层**：数据是否已经保存到本地；
- **内存层**：数据是否已经成为可使用的对象。

把两层分开，才能在大量数据下同时兼顾启动速度与内存占用。

## 3. Transaction：同步系统的核心抽象

当用户修改一个字段并保存时，系统不会只发送一个普通的 `PATCH` 请求，而是把变化封装成 Transaction。

Transaction 会记录修改内容和必要的旧状态，因此可以支持：

- 乐观更新；
- 失败回滚；
- 离线缓存与重发；
- Undo / Redo；
- 等待服务端最终确认。

典型过程如下：

```text
issue.title = "New title"
  → 内存立即显示新标题
  → issue.save()
  → 创建 UpdateTransaction
  → 写入 IndexedDB 中的事务表
  → 进入 TransactionQueue
  → 批量发送到服务器
```

如果此时断网，事务仍保存在本地；恢复连接后，队列可以继续发送。

这里也存在一个重要工程边界：重试不自动等于“恰好执行一次”。涉及支付、发信、创建外部资源等非幂等操作时，仍然需要事务 ID、幂等键和服务端去重。

## 4. syncId 与 Delta Packet

Linear 的同步并不是让多个客户端自由合并全部状态，而是由中心服务器确定变化顺序。

服务器为已确认的变化分配单调递增的 `syncId`。它类似同步日志的版本号：

```text
syncId 1041 → 修改 Issue A
syncId 1042 → 新增 Comment B
syncId 1043 → 移动 Issue C
```

客户端保存自己的 `lastSyncId`，因此能够判断：

- 当前已经同步到哪个位置；
- 收到的变化是否乱序；
- 中间是否缺少数据包；
- 本地事务是否已经得到服务器确认。

服务器执行事务后，会把实际变化封装成 Delta Packet，再通过连接广播给相关客户端。

Delta 不一定与客户端提交的 Transaction 完全相同。服务器可能同时更新时间戳、生成历史记录，或者触发其他副作用。因此客户端最终仍以服务端广播的结果为准。

这套机制更接近“中心服务器确定全序”的同步模型，不能简单等同于去中心化 CRDT，也不能直接推导出它适合通用富文本协作。

## 5. 权限不是隐藏按钮，而是控制数据分发

同步系统中的权限问题不只是“用户能否打开某个页面”。真正的问题是：不该看的数据是否已经到达了客户端。

Linear 研究中出现的 SyncGroup，把权限范围纳入同步协议：

```text
用户身份 / 团队 / 角色
  → 决定订阅哪些 SyncGroup
  → 服务器只分发对应范围的数据
  → 客户端只保存有权获得的 Model
```

当用户获得新权限时，客户端可以加载新增范围；当权限被撤销时，停止订阅并清理相关本地模型。

这比“先下载所有数据，再用前端隐藏”安全得多。但它仍有现实边界：如果设备已经离线，服务器无法神奇地远程抹除其旧副本。敏感数据还需要过期策略、加密、设备管理和审计共同保护。

## 6. 这套技术如何用于 AI Native 产品

Linear Sync Engine 不只适合任务管理软件。它的很多设计可以迁移到 AI Agent、知识库和工作流产品。

| Linear 中的机制 | AI Native 产品中的对应设计 |
|---|---|
| Model | Conversation、Task、AgentRun、ToolCall、Artifact |
| Transaction | 用户指令、状态修改、Agent 行为请求 |
| IndexedDB | 本地会话、草稿、执行队列和结果缓存 |
| TransactionQueue | 待执行或待上传的 Agent 操作 |
| syncId | 服务端事件序号、审计日志位置 |
| Delta Packet | 流式状态变化、工具结果和任务进度 |
| SyncGroup | 租户、项目、角色和数据权限边界 |
| Undo / Redo | 撤销尚可逆的 Agent 操作 |

一个可靠的 Agent 操作链可以设计成：

```text
用户要求 Agent 执行任务
  → 客户端创建 Pending Action
  → 本地持久化
  → 服务端检查权限与幂等键
  → Agent 调用工具
  → 写入不可篡改的事件记录
  → 客户端接收增量状态
  → 成功确认，或失败回滚
```

尤其重要的是：AI 生成了一个操作，不代表系统必须立刻执行。Transaction 层可以承载权限检查、人工确认、审计、重试和回滚，把模型推理与有后果的动作隔离开。

## 7. 从技术研究到内容产品

这项研究的另一层价值，是它没有停留在一篇很长的技术文章。

它逐步形成了三层内容：

```text
完整逆向研究
  → 给需要验证细节的工程师

十分钟 SUMMARY
  → 给想快速建立整体认知的读者

12 个互动实验
  → 给需要通过操作理解抽象机制的学习者
```

这就是内容产品化：同一份知识，不是机械地改写成长文、短文和视频，而是针对不同理解深度，设计不同的使用方式。

### 7.1 完整研究是可信度底座

仓库保留源码注释、概念映射、架构图和推理过程。读者可以检查结论从哪里来，也可以通过 Issue 或 Pull Request 纠错。

### 7.2 SUMMARY 负责降低入口门槛

不是所有人都会直接读完长篇逆向分析。简明摘要先说明 Model、Transaction、Delta 和同步流程，让读者建立地图，再决定是否深入。

### 7.3 互动实验把不可见过程变得可见

同步顺序、乐观更新、离线队列和权限分发都发生在系统内部。互动实验通过滑块、状态变化和判断题，把这些不可见机制转化为可观察行为。

每一关基本遵循同一个产品结构：

```text
提出问题
  → 操作模拟
  → 观察差异
  → 解释原理
  → 判断题确认理解
  → 回到原始研究
```

它还把进度保存在本地浏览器，不要求注册；同时明确实验做了哪些简化、哪些能力没有实现。这些细节让它更像一个学习产品，而不只是带动画的文章。

## 8. 如何复用到个人技术品牌

如果要围绕 AI Native 与 AI 业务安全持续创作，可以复用这套生产链：

```text
真实问题或技术研究
  → 完整技术文章
  → 三分钟摘要
  → 一个可操作实验
  → 产品开发记录
  → 社交媒体切片
```

例如“AI Agent 工具越权”可以拆成：

1. **技术文章**：解释 Planner、Tool Call、权限令牌、人工确认和审计链。
2. **互动实验**：切换最小权限、自动执行和人工确认，观察同一请求产生的不同结果。
3. **产品记录**：公开需求判断、原型、失败方案和迭代过程。
4. **短内容**：提炼一个反直觉结论，引导读者回到完整实验。

这样做的结果不是“多发几篇文章”，而是把研究沉淀成可以体验、引用和持续迭代的产品资产。

---

## 9. 最终启示

Linear Sync Engine 给出的技术启示是：

> 快速体验来自本地即时反馈，可靠性来自持久化事务、服务端排序、增量同步和权限边界。

围绕它产生的研究与互动实验，则给出了内容产品化启示：

> 深度内容负责建立可信度，摘要负责降低门槛，互动体验负责让理解真正发生。

对独立开发者而言，两者可以合在一起：研究真实技术问题，把结论做成可运行的小产品，再公开记录构建过程。技术因此不再只是笔记，内容也不再只是文章。
