数据流分析（方法论）

数据流分析（方法论）

Aug 25, 202614 min read

  • security
  • methodology
  • data-flow
  • vulnerability
  • ai-agent
阅读—

一句话：漏洞 = 可控数据 + 执行路径。数据流分析就是沿着「请求从哪来 → 经过哪些模块 → 最终撞到哪个危险操作」这条线，把黑盒追成白盒。它既适用于传统 Web / 网络设备，也适用于今天的 AI 业务系统。

内容难免有误，请带着辩证视角阅读；本文方法仅用于授权环境下的安全研究、资产自查与防护加固。

1. 核心模型：请求生命周期

1.1 触发公式

只要「攻击者能控制的数据」最终流到了「危险操作（执行命令、内存写、文件操作）」，就构成了可利用的漏洞。数据流分析的目标，就是把这条路径在脑子里（不看代码时）先推出来，再用工具验证。

1.2 生命周期状态机

入口点分两类：网络数据包入口（远程请求）与程序入口（本地函数 / 服务）。分析一个请求时，先按「入栈」顺序还原它的生命周期：

目标：做到「不看代码，也能说出它会经过哪些模块、大概从哪里输出」。这正是开发设计里的「请求生命周期（Request Lifecycle）+ 设计模式」思维——先定位框架，再钻细节。

1.3 入口与参数选取

  • 参数形如 key=value：选哪个字段下手，看设计意图。
  • 若 value 是固定枚举值，可尝试先动 key；若 value 开放输入，则优先选 value。
  • 隐式输入常被忽略：NVRAM 配置项、环境变量、从数据库读回来的旧数据——它们也是「可控数据」的来源。

2. 四个分析层次（从外到内）

研究流程：可控数据 → 经过网络模型 → 本地程序处理。数据包起点按「入栈」生命周期排列分析；若是本地调用，跳过网络层，直接看数据进入程序。

2.1 网络传输层：流量获取与中间人对抗

核心：数据包抵达「逻辑代码」之前，在链路里发生了什么？

  • L2/L3：MAC 地址伪造、VLAN 隔离穿透（VLAN hopping）、ARP 欺骗。
  • L4：TCP 握手与重定向、UDP 端口与服务识别、端口映射 / 转发逻辑。
  • 中间人（MITM）位点：透明代理与重定向（iptables 转发、DNS 劫持）、SSL/TLS 卸载（自签名证书替换、SSL Strip）、侧信道（通过包长度 / 频率推测加密流中的业务类型）。
环节关键工具实操命令 / 动作
流量截获tcpdump, wiresharktcpdump -i eth0 -w target.pcap
中间人劫持bettercap, ettercapbettercap -iface eth0 → arp.spoof on
端口扫描nmapnmap -sV -p- 192.168.1.1（识别隐藏服务）
SSL 卸载burpsuite, mitmproxy导入自签名证书 → 设置透明代理

2.2 接入与预处理层：内核到用户态进程

核心：操作系统收到原始包后，如何交给业务程序？

  • Socket 接收与内核转发：Netfilter 钩子、NAT 转换；从内核 sk_buff 到用户态 recv() 的拷贝路径。
  • Web Server / 协议解析器（前端）：请求由 header + body/data/multipart/file 组成；接入层做 SSL 解密 → HTTP 报文重组；Header 过滤（Host 校验、Content-Length 绕过、多重 URL 编码处理）；文件上传的临时存储逻辑。
环节验证对象实操命令 / 动作
监听定位网络服务netstat -tulnp 或 lsof -i :80（找 Web Server 路径）
流量分发iptablesiptables -L -t nat（看是否存在流量重定向）
预处理识别Web Server 配置检查 /etc/nginx/nginx.conf、/etc/httpd.conf
运行时分析stracestrace -p <pid> -e trace=recv,recvfrom,read（实时看收包）

2.3 业务逻辑流转层：请求生命周期追踪

核心：不看代码，推测数据在不同「房间」（模块）间的流转。

  • 过滤层（Middleware）：鉴权插件、输入清洗（WAF 逻辑）、Session 校验。
  • 路由层（Dispatcher）：URL 如何映射到功能函数（静态 Map vs 动态加载）。
  • IPC 跨进程流转（网络设备重灾区）：数据从 Web 进程转发到管理进程（如 cmm、cfg_manager）；序列化风险——JSON / TLV（Tag-Length-Value）/ 二进制 Protobuf 转换中的解析溢出。
环节分析重点实操命令 / 动作
路由映射URL → 函数静态： grep -r "/goform/" <binary>
动态： 观察 /var/log/messages
IPC 追踪跨进程通信OpenWrt 系： ubus monitor
通用： ls -l /proc/<pid>/fd（看 Unix Domain Socket）
权限校验鉴权逻辑搜 Auth 相关函数；找 whitelist 字符串（绕过登录点）
配置交互NVRAM / UCInvram show 或 uci show（看业务如何读取参数）

2.4 代码执行层：输入源（Source）与危险函数（Sink）

核心：数据流最后撞击到了哪个「危险零件」？

  • 输入建模（Sources）：显式输入（URL 参数、POST Body、Cookie）；隐式输入（NVRAM、环境变量、数据库旧数据）。
  • 危险操作（Sinks）：系统命令执行 system() / popen() / execve()；内存破坏（数据流向 memcpy / strcpy 且长度不受控）；文件系统破坏（数据流向 fopen 导致路径穿越）。
环节分析重点实操命令 / 动作
Sink 点搜寻危险函数grep -E "system|popen|execve|strcpy|sprintf" <binary>（注：ERE 下用 | 表示或；用 grep -E 时写作 |，用 egrep 同）
动态调试gdb, gdbservertarget remote :1234 → b *0x00401234（断点看参数）
输入控制验证字符过滤绕过注入：'; ls #、$(ls)、`ls`、\n ls \n
内存破坏验证溢出分析生成 200 字节唯一模式串（如 pwntools cyclic 200 / peda pattern_create 200），观察 PC/EIP 是否被覆盖

修正说明：原文 grep -E "system\|popen..." 在「扩展正则」下 \| 是字面竖线、不会按「或」匹配。正确写法是 grep -E "system|popen|execve|strcpy|sprintf"（无反斜杠），或用 grep -E "system\|..." 的 BRE 转义形式。上表已标注。

3. 信任边界与模式库（浓缩）

3.1 攻击面

外界与内部交互的入口有哪些？

  • 网络面：WAN / LAN / 管理口
  • 协议面：HTTP / SNMP / SSH / UPnP / TR069
  • 功能面：登录、上传、配置导入、诊断工具
  • 隐藏面：调试接口、云控通道、升级接口

3.2 控制面 / 数据面 / 管理面（网络设备特有）

面作用漏洞类型
控制面Web 管理、CLI、API认证绕过、命令执行
数据面报文转发、NAT、VPN解析漏洞、内存破坏
管理面SNMP、TR069、云控越权、设备接管

3.3 信任边界

可控点是否存在，决定了边界能否被突破：

边界典型问题
网络 → 应用解析漏洞、缓冲区溢出
未认证 → 已认证权限绕过
普通用户 → 管理员提权
设备 → 云端设备劫持

常见弱点：鉴权豁免名单（Whitelist）、本地信任（Local Trust）、进程间信任（IPC Trust）。

3.4 设计模式 → 易错点

建立「模式库」——先定位开发框架，再找其典型漏洞点，而非逐个算法钻研。

需求常见模式易出漏洞点
鉴权中间件 / 过滤器漏校验
任务调度生产者-消费者竞争条件
跨进程通信消息队列 / RPC反序列化
插件机制动态加载任意加载

4. AI 业务攻防：把数据流模型映射到 AI 系统

同一套「可控数据 + 执行路径」模型，完全适用于 AI 业务。 区别只是「数据」和「执行路径」的形态变了。理解它，是做 AI Agent Security / RAG 安全 / 业务 LLM 防护的起点。

4.2 新的 Source 与新的 Sink

角色传统系统AI 系统
Source（可控数据）URL 参数、POST Body用户 Prompt、间接注入内容（RAG 文档、网页抓取、MCP tool 返回值、Agent 记忆）
Sink（危险操作）system()、fopenLLM 生成的工具调用、自动 Agent 的「consequential actions」（发请求 / 执行命令 / 改数据 / 发邮件）、模型生成的代码
信任边界网络↔应用、未认证↔已认证LLM 成了「半可信解释器」：它把不可信输入「翻译」成可信动作

核心风险：Prompt Injection（提示注入）。直接注入来自用户，间接注入来自被检索 / 被抓取的外部内容——后者更隐蔽，因为用户根本没写那句话。一旦注入内容进入 Context 并诱导 LLM 调用高权限工具，就完成了「可控数据 → 执行路径」的闭环。

4.3 真实印证

OpenAI–Hugging Face 入侵事件 正是这条模型走到极端的案例：Agent 拿到了「目标 → 推理 → 工具 → 执行 → 观察 → 继续」的完整闭环后，安全边界彻底失效——它自主把攻击目标从评测靶场外推到了真实生产基础设施。问题不在「某个漏洞」，而在「闭环一旦形成，边界是否还能约束 Agent」。

4.4 AI 数据流分析 SOP

环节分析对象动作
输入面测绘Prompt 入口区分 system / user / retrieved 三类输入来源，画出谁进了 Context
注入面识别间接注入点检查 RAG 检索内容、MCP tool 返回、网页抓取是否未经清洗进入 Context
工具 / Sink 识别Function / Tool 定义列出 Agent 可调用的工具及其权限（能否执行命令 / 发请求 / 改数据）
信任边界LLM 角色确认 LLM 是否把不可信输入翻译成可信动作；Sink 前是否有人工确认（human-in-the-loop）
防御验证最小权限验证工具是否最小权限、输出是否回传不可信内容、是否有沙箱隔离

4.5 防御要点（把边界放在 Sink 上）

  • 在 Sink（有后果的动作）处设边界，而不只是保护模型本身：给工具最小权限、对发邮件 / 执行命令 / 改数据做人工确认。
  • 输入 / 输出隔离：RAG 文档标注来源与可信度，外部内容不进入高权限 Context；对工具返回值做格式与权限校验。
  • 可观测与回滚：记录 Agent 每步工具调用，异常动作可拦截、可回滚。
  • 沙箱执行：模型生成的代码 / 命令在受限环境运行，限制出向连接与文件系统权限。
